# 实验笔记更新规范（exp_x 系列）

## 目标文件

```
czy/exp1/exp1.md
```

这是本项目统一笔记路径，目录名 `exp1` 不代表正文只能记录 exp_1。模型放 `czy/data/{编号}/`，证据放 `czy/exp1/artifacts/{编号}/`；用户明确指定其他路径时按其要求。

## 当前项目：Holosoma / Flux

- `exp0` 是用户指定的首次云端流程验证基线；其三次任务尝试合并记录在 §7，逐次保留失败原因、修复和最终成功证据。后续新目标默认使用 `exp_1`，不将这次基线擅自改名。
- 云端操作使用 [flux-cli](../flux-cli/SKILL.md)，CLI 为 `flux`；RL 启动命令仍为 `gm-run`。操作账号以当次用户指定为准，笔记中保留实际邮箱、用户 ID、项目和任务 ID。
- 保留下面的七节模板，参数名采用 Holosoma 的实际字段（如 `training.num_envs`、`algo.config.num_learning_iterations`），配置和奖励权重优先从该 checkpoint 的 `experiment_config` 获取，不能用当前源码默认值冒充历史运行配置。
- 区分流程测试与策略训练：流程测试验收 CUDA、指定迭代、checkpoint、ONNX 和正常退出，不套用模板示例的奖励阈值、3000 轮或 F1/X1 的奖励名。2 次迭代不能证明行走能力或收敛。
- 平台曲线缺点时标注缺失，并保存脱敏云日志作为来源；不得插值成平台实测点。未录视频、未做回放或未导出 CSV 时如实写明。

**分工**：

| skill | 职责 |
| --- | --- |
| **lab-notebook（本 skill）** | 编号、索引表、实验章节结构、写回结论 |
| `isaac-diag-eval`（可选） | 跑 `eval_isaac_diag.py`，产出 E1~E8 诊断数值（需 CSV，无 CSV 时用训练日志数据） |

新建/更新实验必须遵循本 skill 的章节模板。`isaac-diag-eval` 仅在当前 checkout 存在相应工具且已有诊断 CSV 时使用；无 CSV 时依据训练日志、平台曲线和产物校验记录。

## 一、实验编号规则

### 1.1 格式（跨版本统一序列）

```
exp_{n}    或    exp_{n}.{m}（微调重试）
```

- **主编号（`exp_{n}`）**：默认 n 从 1 开始全局递增（exp_1、exp_2…），每个新实验占一个新编号；用户明确指定编号时优先遵循，当前已指定基线为 `exp0`。
- **微调（子编号 `.{m}`）**：`exp_{n}` 未达标 → 微调优化重训 → `exp_{n}.{m}`（m 递增）；仍不达标 → `exp_{n}.2`…
- **历史兼容**：后续记录统一使用 `exp_{n}`，微调用 `exp_{n}.{m}`，不再添加 `ada`。已有 `exp_ada_{n}` 与旧项目 exp0/exp0.1/exp0.2 的历史正文和数据目录保留，不自动改名。确定下一个编号时同时检查当前项目已有新旧编号，按最大数字递增；其他项目的示例编号不占用本项目编号。

| 示例 | 含义 | 何时使用 |
| --- | --- | --- |
| `exp_1` | 本项目系列首个实验 | 仅在本项目无历史编号时使用，不预设已占用 |
| `exp_2` | 下一个新实验 | 新目标/新方向 |
| `exp_2.1` | exp_2 的微调1 | exp_2 未达标，小改重训 |
| `exp_3` | 再下一个 | exp_2（或其微调）达标后开新方向 |

**规则**：
- 编号不可变：失败尝试保留编号，索引表状态标「失败」，不删除不跳号
- 已有编号保留，补充结果可原地更新；默认新实验用 exp_x，用户明确指定编号除外。

### 1.2 微调（子编号 `.{m}`）

`exp_{n}` **未达标**时，修改参数后重训 → 新建 `exp_{n}.{m}`（m 递增）：

- 微调范围：仅改 1~3 项奖励权重、小参数、小幅修正
- 微调继承父实验的修改编号（见 §3）

### 1.3 新实验（新建主编号 `exp_{n+1}`）

满足**任意一条**时，新建主编号：

- `exp_{n}` 或其微调 `exp_{n}.{m}` **达标验收目标** → 新建 `exp_{n+1}` 设新目标
- 跨 ≥2 个模块的大改（新增/删除奖励、改 IK 逻辑、改 URDF）→ 即使未达标也新建主编号
- 切换训练任务（如 Flat → Rough）→ 新建主编号并在 §5 标注 task 变化

### 1.4 原地更新（不改编号）

满足**任意一条**时，不新建编号，直接更新现有实验的 §7：

- 训练中途观察日志，仅做趋势分析（未训完）
- 训练完成后补充结果数据
- 发现记录有误，修正数值
- 同一个checkpoint重新回放：补充该实验§7，不新增训练实验；若历史编号含ada，可使用去掉ada的同号归档别名（如exp_ada_2 → exp_2），在笔记注明映射并保留旧产物。

## 二、索引表更新规则

文件顶部 `## 实验索引` 表格，**每新建实验必须先加一行**：

| 列 | 必填 | 说明 |
| --- | --- | --- |
| 编号 | ✅ | 如 `exp_2` |
| 日期 | ✅ | `YYYY-MM-DD` |
| 摘要 | ✅ | 一句话：改了什么、结果判定 |
| 状态 | ✅ | 见下表 |
| Task ID | ✅ | Flux 任务 ID，如 `TASK_20261028_224`；重试任务在正文逐次列出 |
| Flux账号 | ✅ | 该实验实际使用的账号邮箱 |
| checkpoint | ✅ | 最终模型文件名，如 `model_3000.pt` |

**状态枚举**：

| 状态 | 何时使用 |
| --- | --- |
| 待训练 | 方案已写，未开训 |
| 训练中 / 续训中 | 正在跑 |
| 已测试 | 训练完成，结论已写 |
| 失败 | 未达验收目标，保留教训 |
| 已废弃 | 方向否定，不再续做 |

## 三、修改内容编号规则

§3「修改内容」内部用**修改一、修改二...** 编号：

- **微调（`exp_{n}.{m}`）**：修改编号**继承**父实验。如 exp_1 有「修改一、二」，exp_1.1 接「修改三」。
- **新实验（`exp_{n+1}`）**：修改编号**重置**，从「修改一」重新开始。

```markdown
## 实验 exp_1（系列首训）
### 修改一：…
### 修改二：…

## 实验 exp_1.1（微调1，继承）
### 修改三：…    ← 接续 exp_1

## 实验 exp_2（新实验，重置）
### 修改一：…    ← 重新从「修改一」开始
```

## 五、Agent 工作流

### 5.1 新建实验

1. **判断编号**：
   - 上一实验**达标**（或跨模块大改/换任务）→ 新建 `exp_{n+1}`（修改编号重置）
   - 上一实验**未达标**且仅小改 → 微调 `exp_{n}.{m}`（修改编号继承父实验）
2. 在索引表**末尾**追加一行
3. 在文件**末尾**追加完整实验章节（§1~§7，§7 占位「待训练完成后补充。」）
4. §1 必须引用上一实验 §7 的**具体数值**，禁止只写「效果不好」

### 5.2 训练完成后更新结果

1. 用 `flux --yes task data keys --task-id ...` 获取实际指标名，再用 `flux --yes task data get` 拉曲线；运行中用 `precise`，终态可用 `precise` 或 `accelerate`
2. 将 Mean reward、Episode length、各奖励项最终值填入 **§7**
3. 写分级结论（✅达标 / ⚠️部分达标 / ❌未达标）
4. 更新索引表：状态 → `已测试` 或 `失败`；摘要补关键判定

### 5.3 训练中途更新（不改编号）

1. 不新建实验，直接在现有 §7 追加「训练进度趋势」小节
2. 索引表状态保持「训练中」

### 5.4 禁止事项

- ❌ 不编造未拉取的数据
- ❌ 不删除失败实验记录
- ❌ 不跳号（exp_2 之后是 exp_3，不要直接 exp_5）
- ❌ 结论禁止笼统「还行」，必须分级 + 量化

## 六、快速决策表

| 场景 | 编号 | 动作 |
| --- | --- | --- |
| 系列首个实验 | `exp_1` | 检查本项目历史；无数据时如实说明 |
| 新方向/新目标 | `exp_{n+1}` | 新建主编号，§3 修改编号重置 |
| 未达标，小改重训 | `exp_{n}.{m}` | 微调，§3 修改编号继承父实验 |
| 训练失败但教训明确 | 原编号 | 更新 §7 + 状态「失败」 |
| 训练中途看日志 | 原编号 | §7 追加趋势，不改编号 |
| 跨模块大改（未达标也新编号） | `exp_{n+1}` | 重置修改编号 |
| 切换任务（Flat→Rough） | `exp_{n+1}` | 新编号，§5 标注 task 变化 |

## 七、注意事项

1. **§1 教训必须可量化**：有上一轮数据时至少列 2 个日志或诊断数值；系列首个实验明确写无历史数据，可列本轮安装重试的耗时和失败阶段
2. **失败同样完整记录 §7**：失败原因写在根因分析
3. **索引表与正文状态一致**
4. **结论分级**：✅达标 / ⚠️部分达标 / ❌未达标，禁止笼统表述
5. **证据来源**：保存查询时间、任务状态、实际曲线 step、原始日志精度和模型 SHA-256；运行时间与纯训练耗时分开记录。脱敏后归档，不保存 API Key 或签名下载 URL

## 八、数据归档规范

`czy/data/{实验编号}/` 只放最终模型及该实验实际生成的部署/回放产物：

| 文件 | 说明 |
| --- | --- |
| `model_{N}.pt` | 训练结果模型 checkpoint，下载后校验大小、iter 和权重有限性 |
| `model_{N}.onnx` | 实际取得并校验的部署模型；仅云端生成而未下载时不能伪造占位文件 |
| `play_output.mp4` | 可选，实际完成回放后归档 |
| `isaac_diag.csv` | 可选，实际完成诊断后归档 |

禁止在该目录存放 `model_isaac_csv.pt`、分析 PNG、日志等中间文件。日志、实际运行配置、曲线、校验 JSON 和回放元数据等长期证据放 `czy/exp1/artifacts/{实验编号}/`，从笔记链接。`exp0` 没有回放视频/CSV，ONNX 只在云端校验通过，因此模型目录仅归档最终 `.pt`。

`czy/analysis/` 仅作为可清理的临时工作目录：部署包、启动脚本、中间CSV和短测产物验证完成后删除；如需留存证据，先迁入对应实验 artifacts 目录并更新笔记链接。后续回放优先使用系统临时目录，结束后清理，不在analysis堆积一次性文件。

Holosoma 小规模入口为 `scripts/train_flux_smoke.py`，验收测试为 `tests/test_flux_smoke.py`；使用前检查文件与当前任务匹配。不要照搬其他项目的 `scripts/amp_tools/` 或 F1/X1 回放脚本。临时请求 payload 成功后清理，长期证据直接写入实验附件目录。
